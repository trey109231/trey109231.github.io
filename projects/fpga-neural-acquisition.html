Build a testable interface before selecting the controller

Rev 1 established the analog stimulation and operator workflow using an AD3. The next architecture investigates Intan recording/stimulation devices and dedicated acquisition hardware, with both a larger headstage path and a compact wireless research system under consideration.

Several controller choices could satisfy the interface on paper. The useful comparison is whether they preserve stimulus timing, drain continuous ADC data, recover from service interruptions and leave enough power and memory budget for the rest of the system. I built chip emulators and common validation tools so each candidate can face the same observable workload.

Cyclone IV emulators as independent instruments

The FPGA models cover the digital interfaces of RHD recording and RHS recording/stimulation devices. They decode SPI commands, return identification and register data, preserve command/response latency, and generate deterministic channel/sample signatures. The RHS model also implements buffered stimulus registers and global U updates.

A simplified per-channel response model generates synthetic AC/DC ADC values from stimulus state, polarity, magnitude, recovery and configured load behavior. This lets a host check the consequences of a command sequence as well as its register echoes. It is a controllable test model of the interface and response, not a validated physiological model.

  • UART diagnostics: conversion, command, protocol-error and malformed-frame counters, plus first-failure framing information.
  • Timing observation: TIM1 records stimulus state transitions and timestamps independently of the acquisition MCU.
  • Repeatable stimuli: prescribed seeds, response bounds and fault controls make failures reproducible.
  • Bounded evidence: the timing trace has finite storage; short timing tests and long integrity tests have distinct verdicts.

The Cyclone IV implementation also required careful timing closure at 25 MHz SPI. First-bit availability, CS handling, return-path delay and clock-domain crossings were practical design constraints. Framing diagnostics helped distinguish incomplete transfers from incorrect sample values; a PHY that simulated correctly still needed a valid fitted implementation and a working board-to-board interface.

Three-link Zynq acquisition baseline

The Zynq-7020 prototype receives two RHD links and one RHS link, builds timestamped records and moves them through FIFOs and AXI DMA to the processing system. Vitis bench applications validate the record fields and every enabled channel. Cyclone UART counters provide a separate view of what each emulated chip received.

A five-minute run completed with 1,250,000 records per link, zero dropped or missing records, and clean emulator framing/protocol counters. That is 3.75 million checked records across the three links at the tested schedule. It establishes this acquisition baseline; it does not establish a completed Ethernet streaming system or the maximum scalable link count.

RP2040: hardware-timed SPI with a software data consumer

The MCU bench runs at a 100 MHz system clock with 25 MHz SPI. A PIO state machine controls CS, SCLK, MOSI and response sampling; chained DMA feeds precomputed command sequences and writes received words into a 4,096-word ring. Core 1 validates and assembles frames. Core 0 drains a bounded export queue into a checksum sink.

All 16 ADC channels run at an average 30 kS/s each while stimulus commands share the same bus. The compiled cadence uses 33.33, 33.33 and 33.34 µs intervals, preserving the 30 kS/s average without moving conversions to accommodate stimulus events. Commands repeat across 10 ms schedule boundaries without a CPU restart.

The stimulus profiles exercise different channel states and include 5 µs and 10 µs spacing between stimulus events. Requested U commits lie on a 1 µs grid for schedules the compiler can fit. This is a demonstrated scheduling capability for admitted workloads, not a guarantee that every arbitrary combination of 16-channel updates fits every microsecond.

Short tests pair MCU sample checking with an independent TIM1 timing verdict. The observed drift-corrected event residual was approximately 0.010 µs worst-case in the supplied runs, at a nominal 20 ns recorder tick. That number describes relative digital observation, including clock-domain crossing; it is not externally calibrated absolute timing or an analog stimulus measurement.

Finding the bottleneck between DMA and exported frames

The first short captures passed, but longer captures exposed a sustained software deficit. At 518,600 response words/s, full validation filled the RX ring in roughly 14 ms; a mode skipping ADC-value comparisons still overflowed in roughly 30 ms. Lag-over-time measurements showed that the common consumer path also needed work.

I used the generated code and explicit work/counter diagnostics to investigate the processing cost. The optimization pass moved the acquisition loop and compact validation references into SRAM, processed guarded private blocks, prepacked ADC bounds, removed extra frame copies and reduced repeated peripheral/status work. The checksum path explicitly uses the ARM multiply instruction.

Both modes retain command checks, sample ordering, overwrite detection and export ownership. The full mode checks every ADC pair; raw mode skips only that value comparison. Their shared transport and export path makes the comparison meaningful.

Each run received 5,186,001 response words. Independent emulator checks confirmed 4,800,000 conversions, 194,003 U updates including initialization, zero malformed words/protocol errors, and the final all-off/recovered state. In stress mode, early samples show the backlog returning to a few words between pauses; the peak remains bounded throughout the run.

The test deliberately adds core-0 memory traffic and core-1 interruptions. It establishes sustained operation under that synthetic workload. Actual Wi-Fi contention, SD-card write stalls and inter-MCU transfers still need to be measured. The long-run counter check also does not replace the short TIM1 event-timing tests.

Verification across software and hardware boundaries

The test suite exercises the assembled PIO program against the actual RHS Verilog, checks the C response validators, and injects corruption, ring overwrite, queue overflow, missing completion and abort conditions. Repeated-schedule seams and the final outstanding DMA write are explicit test cases. Native sanitizer checks complement the on-board runs.

The result is a reusable acquisition engine and an independently observable target. The next controller can change without discarding the protocol tests, waveform profiles, counter checks or timing analysis.

The wireless controller comparison

The current candidates will be evaluated against a common workload and PC-side protocol. The choice depends on whether the experiment needs continuous streaming, occasional transfers or local recording, as well as measured power and integration effort.

Planned work includes a more flexible Zynq-based emulator, live schedule updates, real wireless/storage traffic and automated PC control. A separate UART or Ethernet diagnostic connection to the emulator will allow the test runner to inspect what reached the chip even if the wireless device stops reporting.

BadRTOS: Preemptive AVR RTOS

A small real-time operating-system lineage that began with a PIC16F84A TinyRTOS-style assembly runtime, then evolved through ATmega168A scheduler experiments into a preemptive ATmega328P RTOS. The PIC version used a Timer0 tick, countdown-based cooperative task timing, heartbeat modes, debounced button input, software PWM, and bit-banged UART telemetry. The final AVR version implements timer-driven preemptive scheduling, manual context switching, separate task stacks, delays, semaphores, mutexes with priority inheritance, mailbox IPC, stack high-water monitoring, and UART diagnostics, then validates those features on real hardware using GPIO traces and serial status output.

Project motivation

The goal of BadRTOS was to understand RTOS behavior from the implementation side rather than only using an existing API. Most production embedded projects should use a proven kernel such as FreeRTOS or Zephyr, but building a small kernel from scratch makes the underlying failure modes much clearer: stack corruption, ISR preemption, context-save bugs, priority inversion, blocking behavior, and timing assumptions are no longer hidden behind library calls.

This project complements my hardware-heavy embedded work by demonstrating the lower-level computer science pieces of embedded systems: scheduling, concurrency, resource ownership, inter-task communication, priority handling, and runtime safety checks.

Project lineage: PIC cooperative runtime to AVR preemptive RTOS

BadRTOS did not start directly as a full preemptive AVR kernel. The proven precursor was a PIC16F84A TinyRTOS-style bring-up runtime written in assembly. It used a Timer0 interrupt for a roughly 4 ms tick, maintained a 16-bit uptime counter, decremented task countdown timers in the ISR, and ran a cooperative foreground loop for heartbeat, button, and telemetry tasks.

That PIC runtime drove a bit-banged 4800-baud UART TX line on RB0, an active-low heartbeat LED on RB1, a debounced active-high button on RB2, and an active-low software PWM LED on RB3. Button presses incremented a counter and cycled both heartbeat mode and PWM mode, while periodic UART telemetry reported tick count, heartbeat state, button state, press count, heartbeat mode, and PWM mode.

The PIC step is worth including because the PIC16F84A is an extremely constrained old part with no hardware UART, limited RAM, awkward banking, and old tooling. Implementing the tiny runtime required direct register control, interrupt context save/restore, software timers, debouncing, software PWM, and cycle-counted UART framing before moving into the AVR scheduler work.

From there, the work moved to AVR scheduler experiments. The ATmega168A version explored real preemption and separate task stacks, but SRAM pressure made the full feature set unreliable. Moving to the ATmega328P provided enough RAM to finish the preemptive scheduler, blocking primitives, mailbox IPC, priority inheritance, stack monitoring, and UART diagnostics.

Implemented features

  • Timer-driven preemptive scheduling on AVR using a Timer1 compare interrupt.
  • Manual AVR context switching in naked assembly, including register, stack pointer, and SREG handling.
  • Static task creation with independent per-task stacks and fake initial stack frames.
  • Priority-based scheduling with equal-priority round-robin behavior.
  • Cooperative yield plus sleep/delay wakeups.
  • Counting semaphores with blocking wait and post behavior.
  • Mutex lock/unlock with priority inheritance for blocked high-priority waiters.
  • Fixed-size mailbox/queue IPC with blocking send/receive and non-blocking helper functions.
  • Stack high-water scanning, minimum-free tracking, and hardware-visible stack fault output.
  • UART runtime status dump showing ticks, counters, task states, priorities, and stack usage.

System architecture

BadRTOS uses a small static task table. Each task owns a stack filled with a known pattern so the kernel can later estimate high-water usage. When a task is created, the kernel builds an initial fake context frame on that stack. The AVR restore path can then enter the task as if it had already been interrupted and resumed.

The scheduler runs from two paths: a cooperative yield path and a Timer1 ISR preemption path. Both save the current CPU context, update the current task's saved stack pointer, select the next runnable task by effective priority, load the selected task's stack pointer, and restore the saved context.

Synchronization and IPC

Semaphores, mutexes, and mailboxes are implemented using the same core pattern: enter a critical section, check whether the operation can complete immediately, block the current task if it cannot, record the waiting task in the object's wait mask, and wake the highest-priority eligible task when the object's state changes.

The mutex implementation includes priority inheritance. When a high-priority task blocks on a mutex owned by a lower-priority task, the owner temporarily inherits the higher effective priority. The scheduler uses effective priority when choosing the next task, so the low-priority owner can run, finish the protected section, and release the mutex instead of being starved by unrelated work.

Hardware validation

The final integration demo exposes key RTOS events on GPIO pins and also prints a UART status report. This made the test observable from both outside the chip and inside the kernel. The Analog Discovery 3 monitor captures mailbox, semaphore, mutex, tick, busy-task, and stack-fault behavior, while UART shows task states, priorities, counters, and stack free space.

Final integration test

The final demo runs multiple tasks at the same time:

  • UART status task: prints a periodic kernel/task status report.
  • Mailbox producer: sends bytes into the mailbox and posts a semaphore.
  • Mailbox consumer: waits on the semaphore, receives bytes, and toggles a receive event pin.
  • Low-priority mutex owner: holds a mutex long enough to create a priority inversion case.
  • High-priority mutex task: blocks on the mutex, forces priority inheritance, then acquires it.
  • Non-yielding busy task: spins forever without calling yield or delay, proving timer preemption works.

This combined test validates the intended feature set: preemption, delays, blocking states, semaphore post/take, mailbox send/receive, mutex lock/unlock, priority inheritance, stack monitoring, and UART diagnostics.

What I learned

The PIC version was a useful first step because it made software UART timing, clock assumptions, interrupt-driven timing, cooperative task structure, debouncing, software PWM, manual bring-up, and old-MCU tooling constraints concrete on a very limited part. The most difficult step after that was moving from simple foreground firmware into real preemptive context switching. Higher-level primitives like semaphores and queues are mostly kernel bookkeeping once stack switching and scheduling are reliable. The fragile parts were the AVR details: how the return address sits on the stack, how SREG is saved and restored, how an ISR-created context differs from a cooperative yield context, and how quickly SRAM pressure can create misleading failures on small MCUs.

The project made RTOS APIs much less abstract. A call like delay, semaphore wait, queue receive, or mutex lock maps directly to task states, wait objects, stack frames, effective priorities, and scheduler decisions.

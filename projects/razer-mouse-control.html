Razer Mouse Control

Two small Windows utilities for configuring a DeathAdder 2013 and Viper Mini directly over USB HID. The project grew from an old mouse teardown into firmware extraction, native and managed host-code analysis, protocol recovery and reversible hardware tests.

A small configuration tool with a much larger investigation behind it

The practical goal was simple: read and change ordinary mouse settings without running the vendor's full application suite. The tools connect to the hardware, inspect its current configuration, apply a requested change and verify it with a fresh read. JSON profiles provide a portable record of settings.

The useful engineering work was discovering what those settings meant on the wire. That required relating device hardware, updater resources, native C++ protocol objects, managed application layers and observed USB transfers.

DeathAdder: from teardown to a coherent firmware image

The DeathAdder teardown revealed an MC9S08JM16, a 16 KiB HCS08 microcontroller with USB support, plus an unpopulated six-pin header consistent with its debug interface. I did not use that header to read the chip. The distributed firmware updater provided the starting image and host-side protocol evidence.

The updater combined a managed .NET front end with a native x86 device library. Its firmware was embedded as UTF-16 Motorola S-record strings rather than a loose binary. Extracting and ordering those address-bearing records recovered a 16 KiB image.

Correct memory mapping was essential. Loading the image at zero produced misleading branches and vectors; mapping it to the HCS08 flash window at 0xC000–0xFFFF aligned the reset and interrupt paths. A PyGhidra annotation helper makes the flash mapping, option-byte labels and reset-vector setup repeatable.

The host library was the most direct route to normal configuration commands. Following exported functions, C++ RTTI and virtual calls identified the HID feature-report path used by the normal mouse and the WinUSB path used after bootloader enumeration.

Viper Mini: finding the serializer inside Synapse

The newer Viper stack contained far more software, but the relevant path was concentrated in its product-specific module. Tracing the device control object to its Protocol 2.5 instance exposed the constructors for polling, current DPI and the hardware DPI-button stage table.

The updater confirmed the feature-report size and device metadata. The product module supplied the configuration serialization. USB captures and comparison with OpenRazer then provided additional checks on framing and command interpretation.

A particularly useful failure involved DPI stage IDs. An early hypothesis treated them as zero-based indexes and sent IDs 0 and 1; the mouse rejected the table with status 0x03. The baseline actually contained IDs 1 and 2. Preserving the firmware-defined IDs fixed the write. The implementation now treats IDs as identifiers and requires the active ID to exist in the supplied table.

One report envelope, different device semantics

Both tools exchange a 91-byte Windows HID feature report: one report-ID byte followed by a 90-byte protocol body. The body carries status, transaction information, command class/ID, payload length, an 80-byte argument area and an XOR checksum.

The transport validates response checksums, status, transaction IDs, command echoes and expected payload sizes. A returned success status alone is insufficient: a fresh semantic readback must match the requested settings.

Independent tools with explicit readback

The two Tkinter applications use independently written Python protocol modules and hidapi. They read hardware state before editing and read it again after Apply. Loading a JSON profile fills the controls; the hardware write occurs only when the user applies it.

Separate command-line tools expose read-only inspection and reversible exercises. Those tests capture the baseline, temporarily change supported settings, verify each change, restore the original state and verify restoration. The DeathAdder GUI also attempts baseline restoration if Apply fails.

What was checked on physical hardware

The DeathAdder tests exercised DPI, polling and wheel-LED writes, read both supported LED groups, and restored captured settings. Explicit bootloader entry was also observed: the normal 1532:0037 HID device disconnected and 1532:110D enumerated through WinUSB. Reconnecting the mouse returned it to normal operation.

The Viper test changed polling, current X/Y DPI and its populated two-stage table, verified those changes, then restored and reread the full baseline. The tested table used 400/800 DPI with stage IDs 1/2. The parser/editor supports up to five stages, but the repository does not claim physical testing of every table size or firmware revision.

USBPcap/Wireshark captures supported the static analysis with observed transfer sizes, field positions and re-enumeration behavior. OpenRazer was a later independent cross-check of the protocol layout and encodings. The published tools remain a separate Windows implementation.

Scope. The tools configure the listed owned devices. Bootloader entry is a separate CLI operation; no erase or firmware-programming implementation is included. Viper lighting and button remapping are outside the implemented feature set.

Outcome

The result is a pair of usable configuration utilities backed by a documented investigation. The strongest part of the project is the chain of evidence: a plausible interpretation from static analysis, an observed USB exchange, then a physical write/readback/restore result.

The public repository contains original Python code, build scripts and derived interface documentation. Vendor binaries, recovered firmware and bulk decompiler output are not redistributed. The full report records packet layouts, the host call paths, rejected hypotheses and remaining limitations.
